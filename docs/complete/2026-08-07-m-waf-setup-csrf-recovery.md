# M-WAF 최초 설정 CSRF 복구 개선

## 확인한 현상

- 실행 중인 `https://192.168.7.200:18443/setup`의 GET 응답은 `200`이며, 서명된 hidden CSRF 값과 `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/setup` 쿠키를 정상 발급한다.
- 관리자 생성이 실행되지 않도록 짧은 비밀번호를 사용한 진단에서 쿠키와 폼 토큰이 일치하면 입력 검증 단계의 `400`으로 진행했다.
- 같은 폼 토큰을 쿠키 없이 제출하면 화면에 보인 것과 동일하게 `403 invalid csrf token` 평문으로 종료했다.
- 따라서 GET 라우팅 문제가 아니라, 만료·차단·다중 탭 갱신 등으로 setup 쿠키와 폼 토큰이 맞지 않을 때 복구 화면이 없던 문제다.

## 반영 내용

- 유효한 setup CSRF 쿠키가 있으면 GET마다 새 토큰으로 교체하지 않고 같은 토큰을 재사용하고 만료 시간을 갱신한다.
- 쿠키가 없거나 서명이 잘못되었으면 새 서명 토큰과 보안 쿠키를 발급한다.
- POST는 기존과 동일하게 서명된 쿠키와 폼 토큰이 모두 일치해야 통과한다.
- CSRF 검증 실패 시 보안을 우회하지 않고 HTTP `403`을 유지하면서, 새 토큰이 포함된 최초 설정 화면과 한국어 복구 안내를 렌더링한다.
- 복구 화면에는 비밀번호를 제외한 사용자명과 표시 이름만 HTML escaping을 거쳐 유지한다.
- setup 화면은 `Cache-Control: no-store`로 반환해 브라우저가 오래된 토큰이 포함된 폼을 재사용하지 않도록 한다.
- 자체 서명 CA가 브라우저에서 신뢰되지 않는 경우 M-WAF CA를 신뢰 저장소에 등록하라는 안내를 추가했다.

## 회귀 방지

- 유효한 setup 쿠키 재사용 및 만료 갱신
- 잘못된 setup 쿠키 교체
- 쿠키 누락 거부와 서명 쿠키·폼 토큰 일치 허용
- `403` 복구 화면, `no-store`, 새 쿠키 발급과 안전한 입력값 유지

위 동작을 확인하는 Go 단위 테스트를 추가했다. 저장소 지침에 따라 자동 테스트와 프론트엔드 빌드는 이 작업에서 실행하지 않았으며, `gofmt`와 `git diff --check`로 정적 형식을 확인했다.

## 배포 주의사항

- 현재 실행 중인 Manager는 아직 기존 바이너리이므로 태그 이미지 생성과 Manager 재배포 전에는 기존 평문 오류 동작이 유지된다.
- 주소 표시줄의 인증서 경고는 CSRF 화면 개선과 별개의 TLS 신뢰 문제다. 운영자 PC가 `mwaf_ca_cert.pem`을 신뢰하도록 설정하거나, 승인된 인증서를 사용하는 관리용 reverse proxy에서 TLS를 종료해야 한다.
- 기존 Agent가 연결된 환경의 CA 파일을 단순 삭제하거나 재생성하면 Agent 신뢰 체계가 끊길 수 있으므로 자동 교체하지 않는다.
- DB 초기화, migration, reset과 관리자 생성은 수행하지 않았다.
