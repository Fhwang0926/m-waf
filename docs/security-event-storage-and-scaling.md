# M-WAF 탐지 이벤트 저장 및 조회 확장 기준

## 현재 저장소

M-WAF는 계정, 기업, 서버, 정책과 탐지 이벤트를 MariaDB InnoDB에 저장한다. 기본 Compose 이미지는 MariaDB 11.8.6으로 고정되어 있고, 탐지 이벤트는 `security_events` 테이블에 보존한다.

기본 운영값은 다음과 같다.

- 이벤트 보존 기간: 30일
- 관리자 화면 조회 범위: 최근 1시간, 24시간 또는 7일
- 이벤트 목록 크기: 페이지당 100건
- Agent 수신: transaction당 최대 500건
- 이벤트 정리: 시작 시점과 기본 1시간 주기, 한 batch당 5,000건
- Manager DB pool: 최대 32개 연결
- 기본 Compose InnoDB buffer pool: 1GiB

## 이벤트 인덱스

현재 테이블은 다음 B-tree 인덱스를 사용한다.

- `occurred_at`
- `(agent_id, occurred_at)`
- `(rule_id, occurred_at)`
- `(agent_id, event_id)` unique

최신 시간 조회, 서버별 조회와 Rule ID 조회는 기존 인덱스를 우선 활용한다. 인덱스를 무분별하게 늘리면 수신 성능과 디스크 사용량이 같이 악화되므로 차단 여부·위험도 인덱스는 실측 없이 추가하지 않는다.

## 이벤트 목록 페이지 처리

관리자 HTML 화면은 2페이지부터 `(occurred_at, id)` 커서를 사용한다.

```text
첫 페이지
  ORDER BY occurred_at DESC, id DESC LIMIT 101

다음 페이지
  WHERE (occurred_at, id) < (마지막 이벤트 시각, 마지막 이벤트 ID)

이전 페이지
  WHERE (occurred_at, id) > (첫 이벤트 시각, 첫 이벤트 ID)
```

동일한 마이크로초에 여러 이벤트가 발생해도 `id`를 보조 정렬 키로 사용해 중복·누락을 방지한다. 커서는 URL-safe Base64로 인코딩하지만 접근 권한을 포함하지 않는다. 모든 요청은 커서와 별개로 현재 세션의 기업 범위를 다시 적용한다.

기존 Admin JSON API의 `page`와 `page_size`는 호환성을 위해 유지한다. `cursor`를 보내지 않은 기존 호출은 종전 OFFSET 동작을 사용한다. 응답에는 다음 필드를 추가한다.

- `has_previous`
- `previous_cursor`
- `has_next`
- `next_cursor`

새 클라이언트는 다음·이전 조회에 반환된 cursor를 사용해야 한다.

## 대시보드 집계 보호

대시보드는 선택 범위에 대해 이벤트 수, 차단 수, 시간 추이와 상위 Rule·URI·서버를 계산한다. 동일한 범위의 동시 요청이 같은 집계를 반복하지 않도록 Manager 인스턴스 안에서 결과를 15초 동안 재사용한다.

- cache key: 기간, 기업, 그룹, 서버
- 최대 항목: 128개
- 만료 데이터는 다음 저장 시 정리
- 최대 항목을 초과하면 cache 전체를 비우고 다시 채움
- DB 또는 공유 cache에는 저장하지 않음

따라서 Manager 재시작과 다중 Manager 인스턴스 사이에는 cache가 공유되지 않는다. 집계 결과는 최대 15초 지연될 수 있으며 원본 이벤트와 정책 판단에는 영향을 주지 않는다.

## 남은 비용이 큰 조회

다음 조회는 현재 MariaDB 구조에서 여전히 비용이 클 수 있다.

- `uri`와 `message`의 `%검색어%` 부분 문자열 검색
- 최근 7일 전체 이벤트의 URI 그룹 집계
- 차단 여부 또는 위험도만 선택한 대규모 시간 범위 조회
- cursor를 사용하지 않는 기존 API 클라이언트의 깊은 `page` 조회
- 보존 기간을 길게 설정한 상태에서 발생하는 대량 정리

현재 자유검색 의미와 토큰화 특성을 유지하면서 일반 B-tree 인덱스만 추가하는 것으로는 부분 문자열 검색을 해결할 수 없다.

## 용량 판단

30일 기준 단순 이벤트 개수는 다음과 같다.

| 평균 수신량 | 30일 이벤트 수 |
|---:|---:|
| 초당 1건 | 약 259만 건 |
| 초당 10건 | 약 2,592만 건 |
| 초당 100건 | 약 2억 5,920만 건 |

실제 저장 공간에는 URI, 메시지, transaction 정보와 보조 인덱스가 포함된다. 행 개수만으로 디스크 크기나 조회 시간을 확정하지 않는다.

## 다음 단계 결정 기준

다음 지표를 실제 운영 환경에서 먼저 수집한다.

- `security_events` 행 수와 데이터·인덱스 크기
- 이벤트 수신 지연과 실패율
- 이벤트 목록 및 대시보드 HTTP p50/p95/p99
- DB CPU, buffer pool hit rate, 임시 테이블과 정렬량
- 시간당 cleanup 삭제량과 보존 기한 초과 행 수
- 자유검색 사용 빈도와 조회 기간

다음 상황이 반복되면 2차 개선을 검토한다.

- 기본 24시간 이벤트 목록 또는 대시보드 p95가 운영 목표를 지속적으로 초과
- cleanup이 다음 주기 전까지 만료 이벤트를 제거하지 못함
- 인덱스와 active working set이 할당한 buffer pool을 지속적으로 초과
- 자유검색이 핵심 운영 기능이 되어 MariaDB 시간 범위 scan이 반복됨

2차 개선은 실측 결과에 따라 선택한다.

1. 차단 여부·위험도·기업 범위용 복합 인덱스
2. 시간 단위 dashboard 집계 테이블
3. 보존 구간 분리 또는 archive
4. 탐지 이벤트만 ClickHouse 또는 OpenSearch로 분리

MariaDB는 계정·기업·서버·정책의 authoritative control-plane DB로 유지한다. 별도 이벤트 저장소는 대량 분석 또는 전문 검색 요구가 확인됐을 때만 도입한다.

## 호환성과 안전 경계

- Agent 이벤트 batch API와 DB 원본 형식은 변경하지 않았다.
- 기존 Admin JSON API 필드는 제거하지 않았다.
- 기업 격리, CSRF, mTLS와 이벤트 중복 방지 방식은 유지한다.
- 이번 1차 개선에는 DB migration, 데이터 backfill, partition, 외부 검색 저장소를 포함하지 않는다.
